Dev mode: code review and a safety floor for your repo

Dev mode watches the repo of every team in a space, on GitHub or any git server. kwant reads each repo and writes a card for every merge, and for every open pull request or merge request on GitHub, GitLab, Gitea and Forgejo, in plain words. A bot that didn't write the code reviews it. In the same space, anything that can reach production asks you first. kwant writes to GitHub only when you press Post to GitHub on a review.

Turn it on

The Dev mode switch is at the top of the sidebar, under the space's name. One press turns it on, with no setup to fill in. kwant finds each team's repo: the team's repo link, or its folder when that folder is a git checkout. It watches all of them, up to 10 per space. It reads this on your machine, with no network. A sign-in token inside a remote address is dropped and never logged or stored.

  • A short note says what it found, such as Watching 3 repos, with Open Dev desk and Undo. When a repo needs you, such as no GitHub connection that can read it, the note adds one button for that.
  • A team with no repo shows as one quiet line on the Dev desk, with Link a repo. Linking a repo never turns Dev mode on by itself.
  • Connect GitHub shows when no GitHub connection can read the repo. It opens the GitHub form right where you pressed it, a popover on the desktop and a sheet on the phone, and Dev mode picks the repo up as soon as the connection is saved, without turning it off and on.
  • Turning on never fails. With no repo, the production floor and the command guards still work, and the desk waits for one.

On the Dev desk, one line says how many repos are watched and how many need you. Show repos opens the list: each team's repo with its branch, where kwant found it, and its state. A repo that needs you has one button for its fix, and the others keep going.

Any git repo

Since 0.7.3, Dev mode reads every repo's history with git: GitHub, GitLab, Gitea, any git server, or a team folder with no remote. Each merge gets its plain-words card. Pull requests, CI checks and reviews need the repo's forge: GitHub, or since 0.7.4 GitLab, Gitea and Forgejo. Post to GitHub works on GitHub repos only. kwant keeps a copy of each watched repo in its data folder, up to 1 GB; a bigger repo reads "Too big to read". The server needs git 2.31 or newer; without it, the desk says "Needs git on the server", with the install tip. kwant fetches over https, http, ssh or git, and never from the server itself, a link-local or a cloud metadata address. git runs as the server user kwant runs as, so that user's SSH keys and credential helpers work.

Under a team's repo link, Team settings say in one line what Dev mode does with it: watched, watched but needs Connect GitHub for reviews, can be watched once Dev mode is on, or read with git.

GitLab, Gitea and Forgejo

Since 0.7.4, repos on GitLab, Gitea, Forgejo and Codeberg get review cards for their merge requests or pull requests, with their CI, like GitHub's. Add the server once in Loose ends with its address and a read token (read_api on GitLab). kwant asks the server which forge it runs, and asks you only when it can't tell. A repo row on the Dev desk with no connection yet has a Connect GitLab (or Gitea, or Forgejo) button that opens the same form in place. The repo list shows where each repo lives.

Posting a review back is still GitHub only: the card says "Posting to GitLab comes in a later update" and links to the merge request. Forge requests take the same address checks as git fetches and never follow redirects.

A repo with no forge, or with no token for it, still gets reviews: each pushed branch that's ahead of the watched one gets a review card, with no CI and no Post.

Before you turn it on

On GitHub, Dev mode reads pull requests and checks through the GitHub connection in Loose ends (its row says "Also used by Dev mode"), so it needs a GitHub token. Reading works with a read-only token; posting a review needs Pull requests: Read and write on a fine-grained token.

Where the token is kept. When some bots run commands without asking (new installs start on Ask only when risky), one of them could read a token saved on this server. The card Before you save the token says so and offers Save it on this server, Use Bitwarden or Make every bot ask first. A read-only token limited to the repos you need keeps the risk small. See Approvals & passwords.

What landed

The Dev desk sits at the top of the sidebar. Its first tab, What landed, has one card per commit that reaches the watched branch: what changed in plain words, how risky it is, the commit, the pull request it came from (or "Direct push"), a diffstat for each file, and whether tests passed.

  • Since you last looked rolls up what's new, and Mark all seen clears it.
  • Draft release notes writes notes from every landed card since the last tag.
  • Verified goes on a merge only when another bot reviewed that exact head in kwant, every finding was fixed or dismissed, and CI on the merge is green. A pull request merged before its review was ready stays "not verified": the sticker says what was checked before the change landed, not after.

kwant checks the repo every 5 minutes. The first check writes up the last 5 merges. Card text is written by one of the space's bots, at most 30 model calls per space per day; the risk, the test checks and CI come from rules and need no model.

Reviews

The Reviews tab has one card per open pull request, written by a bot that didn't write the code, on a different engine when the space has one. A new push to the pull request gets a new review.

Since 0.7.7, Dev mode reviews only fresh work: a branch or pull request gets a review card only if it moved in the last 7 days, so old branches don't fill the desk or spend model calls. Cards on branches that went quiet go stale, and a new push brings a branch back. The newest are reviewed first, and Dev mode's status says how many old ones it skipped.

  • Risk with its reasons, from rules, not from the bot's opinion.
  • Does it do what was asked: what the task asked for, what's missing, and what wasn't asked for.
  • Tests weakened: a removed or loosened test is flagged with the lines.
  • Secrets and packages: Gitleaks runs over the pull request, and every new package is checked against its registry. A found secret or a package that doesn't exist always makes the card High risk. The secret itself is never shown.
  • Findings: Fix it sends a finding to the bot that wrote the pull request, and Dismiss sets it aside.

When the reviewer found nothing to fix, the card gets an LGTM stamp.

Checked with fresh eyes

Since 0.8.0, Dev mode reviews and the Swarm Auditor run in a fresh turn with no chat history and no reviewer memories. The reviewer sees the change, the task and the checks, not the conversation that produced them, so it judges the work on its own. Each review shows a Checked with fresh eyes chip.

The pre-push card

Before a bot's git push, or a GitHub tool that writes files to a branch, kwant shows a pre-push card and runs the checks: a found secret, a new package the project doesn't list, and a weakened test. The push goes ahead only when they're clear.

  • Run the checks again re-runs them after the bot fixes what they found.
  • Push anyway needs your reason (at least 10 characters). It covers that one push only, and the reason is saved on the card.
  • A GitHub file write must name its branch, so the card always says where the change goes.

Post to GitHub

Post to GitHub puts a review card on its pull request as one GitHub review comment, posted as you and pinned to the commit that was reviewed. Findings you didn't dismiss go on their lines when the lines are in the diff; the rest go in the review's text.

  • Only your press posts. kwant never approves, requests changes or merges, and a bot can't post.
  • Secrets are never posted. A found secret is posted only as "Possible secret in" its file and line, and keys and tokens in a finding are replaced with [redacted].
  • Once only. A double click makes one review, and a posted card stays posted.
  • New commits? If the pull request moved on since the review, nothing is posted, and a new review is on its way.
  • Read-only token? The card says your GitHub connection is read only, and nothing is posted.

The production floor

In a space with Dev mode on, these steps always show an approval card first, whatever the space's or the bot's approvals say, and even after "always allow":

StepFor exampleNeeds a backup
Push to the watched or a protected branchgit push to main, master, production and the like, or gh pr mergeNo
Force pushgit push --force to a protected branchNo
Delete a branch or tagDeleting a protected branch or a release tagNo
Deploywrangler, fly, vercel --prod, kubectl, terraform apply, a script named deploy, ship or releaseNo
Migrate productionA migration that names a production database or environmentYes
Destroy dataDROP, TRUNCATE, a DELETE with no WHERE, docker volume rmYes
Use a production connectionAny tool on a connection you marked productionNo
  • No "always allow". Allowing a floor card covers that one call, and the next one asks again.
  • Back up first. A step that can change production data can't be allowed until the space has a backup from the last 10 minutes. The card's Back up first runs the space's backup command, and kwant checks that it wrote a new backup file.
  • Mark a connection production in Connections to make every one of its tools ask, such as a GitHub app that could write to main directly.

The floor reads commands and tool calls, never what a bot says about them. It can't see inside a script with a harmless name, a command built from variables, or a deploy done through a provider's API from code. When a connection can reach production, mark it production.

Bots can't act on a pull request's text

Anyone who can open a pull request writes its title, text and diff. So the bot that writes a Dev mode card runs with no tools at all, on every engine: no MCP servers, no browser, no shell, files or web search. A turn that can't run that way fails instead of running with tools, and the card keeps its rule-based parts.

Work from Jira tickets

Dev mode can take work from Jira Cloud or Jira Data Center. It's off until you connect it, and until then nothing changes. Set it up in Settings › This space › Dev mode, or from the hint on the Dev desk.

  1. Paste your Jira address, like yourcompany.atlassian.net. kwant tells Cloud from Data Center.
  2. Paste a token. On Cloud, make an API token in your Atlassian account under Security › API tokens, with your account's email. On Data Center, open your profile › Personal Access Tokens. Your bots see what you can see in Jira. Nothing is saved until the check passes.
  3. Choose the tickets. Pick the projects, then how a ticket is handed over: with a label (kwant unless you change it), by assigning it to a Jira user you pick, or with your own Jira search. A label keeps the real owner as assignee, and removing it takes the ticket back.
  4. Choose the team that works on these tickets. Its lead writes the brief.

A bot reads each ticket, and the Confluence pages it links to, then writes a brief: the goal, the done-when lines, where in the code, a plan and its questions. Every line names its source. It asks what's unclear, then builds. Turn on Wait for my OK to approve every brief first. Tickets that were already handed over when you connect wait for your Start.

The card follows the ticket through review to landed. It shows Matches the ticket only when every done-when line is met. A token Jira rejects, an address with no Jira, a token that sees no projects, and Jira asking kwant to slow down each get their own message.

Jira only changes when you say so. Comments on tickets are off unless you turn them on, and your bots never move or close tickets. Turning it off pauses tickets in progress and keeps their cards, branches and briefs.

Turn it off

Turning Dev mode off takes two presses. The first press changes the switch to Off? and says Press again to turn off. A second press within 5 seconds turns it off. Escape, clicking elsewhere or waiting keeps it on. The off note has Turn back on.

Off stops the checks, the reviews and the production floor. The cards stay readable, and your approval settings stay as they were.

On your phone

The Dev desk works on a phone too. Its row in the sidebar counts the reviews that are ready since you last opened the desk, and the count is the same on the phone and the desktop.

Only you can see it. Bots can't read the Dev desk, its settings or its cards, because the settings hold the backup command and the cards hold the repo's diffs. None of it is in a space or bot export.
